# ch02｜Agent Swarm 的結構語法：角色、任務、介面

## 這章在講什麼

- 把「一個超聰明但不負責的員工」拆成三個角色：Planner 動腦、Executor 動手、Monitor 長眼；每個角色有明確輸入輸出與工具箱，出錯時才找得到是哪一環。
- Planner 的產出不是清單而是 DAG：節點是原子任務、邊是依賴，圖的形狀直接決定哪些步驟可以並行。好的 DAG 要能檢查四件事：完整、最小、可執行、可觀測。
- Monitor 盯三種異常訊號：數據異常、進度異常、邏輯異常；發現後要被動回報人類還是主動補救，取決於風險高低，也是責任歸屬問題。
- 任務細微性：原子任務（單一輸入、單一輸出、可獨立測試、時間可預測）與複合任務（子 DAG 的封裝與重用）之間要權衡，封裝太深會變成黑盒子。
- 介面分三層：訊息層要有 Schema 版本控制與「寬容的接收者」（不認識的欄位就忽略）；記憶層混用向量記憶（模糊語義）與符號記憶（精確事實）；工具層讓角色只用自己的工具。
- 反方：過度規範化會讓系統僵化（作者以 Kubernetes 的 YAML 地獄為例），要在鬆耦合與強一致性之間依場景調整。

## 作者做過的實驗／例子

- 一位工程師為醫療數據新創寫了約三十行的 JSON Schema 角色定義檔，把單一黑盒模型拆成 Planner／Executor／Monitor，十七個代理各司其職。
- 電商分析任務的 DAG：A 取數據 → B 清洗 → C 趨勢 → D 前十名品類 → E 競爭數據；F 宏觀分析也只依賴 B，所以 E 與 F 可並行；G 綜合 D、E、F 選出三個品類，H 寫報告。
- Monitor 三種訊號的例子：某品類一個月銷售額暴增 500% 卻找不到原因（數據）、預估 5 分鐘的節點跑了 30 分鐘（進度）、D 說成長最高而 F 說宏觀趨勢負面（邏輯）。
- Kubernetes YAML 地獄：設定檔數量多、層次深、彼此依賴，花在寫設定的時間比寫程式還多。

## 教練解說要點

- DAG 是 Planner「可被驗證」的輸出：拿掉一條邊或多一個循環，程式就能抓到，這是單一黑盒模型做不到的。
- 並行的收益來自圖的形狀（E、F 並行），不是來自代理數；關鍵路徑才是總時間的下限。
- Monitor 的授權範圍要依風險設定：高風險只報警、低風險可自動重跑，自動修正也可能過度修正。
- Schema 版本號與寬容接收者讓系統能演化；但欄位越細越容易走向 YAML 地獄。

### 練習 1：跑一次 Planner／Executor／Monitor，比較被動與主動 Monitor

**目的**：在書中的電商 DAG 上看見並行縮短時間，以及 Monitor 三種異常訊號在被動／主動兩種授權下的差別。
**送給練習視窗的提示詞**：

```text
寫 ch02/interactive/triad_sim.py（只用標準庫，random.seed(202)，不可 input()，30 秒內跑完）：
1. 內建 DAG：A(無) B(A) C(B) D(C) E(D) F(B) G(D,E,F) H(G)，每個節點預估時間 5 分鐘。
2. Executor：有 2 個 executor，用簡單的事件模擬（模擬時鐘，不真的 sleep）依拓撲順序排程，實際時間 = 預估 × random.uniform(0.8, 1.3)。
3. 注入三種異常（固定注入，方便重現）：
   - 節點 C 的輸出含一個品類月增 500%（數據異常，門檻：月增 > 300% 且無促銷標記）。
   - 節點 D 實際時間改成 30 分鐘（進度異常，門檻：> 預估 × 3）。
   - 節點 D 輸出「品類 X 成長最高」、F 輸出「品類 X 宏觀負面」（邏輯異常：同一品類結論相反）。
4. Monitor 兩種模式各跑一次：
   - passive：只記警告，等「人類」處理，每個警告讓流程延遲 60 分鐘（模擬下班時間沒人回）。
   - active：數據異常自動重跑 C 一次（重跑後異常消失）、進度異常自動換另一個 executor 重跑（時間恢復正常）、邏輯異常仍需人類（延遲 60 分鐘）。
5. 另跑一個基準：只有 1 個 executor（不能並行）、無異常。
6. 印出：每次執行的總完成時間、關鍵路徑、E 與 F 是否實際重疊執行、警告表（時間｜節點｜異常類型｜處置）。結果另存 ch02/interactive/triad_result.json。
```

**觀察重點**：

- 2 個 executor 時，E 與 F 的時間區間是否重疊？總時間是否比 1 個 executor 短？
- 三種異常是否都被偵測到，類型標示正確？
- active 是否比 passive 快很多，但邏輯異常在兩種模式下都還是要人類處理？

### 練習 2：讓真實模型當 Planner，用版本化訊息交出 DAG

**目的**：讓真實模型扮演 Planner，輸出包在版本化訊息信封裡的 DAG，再用程式檢查四個判準與 Schema 相容性。
**送給練習視窗的提示詞**：

```text
寫 ch02/interactive/planner_agent.py（只用標準庫）：
1. 用 practice/llm_agent.py 的 ask_json 呼叫 claude -p 一次。提示詞：你是 Agent Swarm 的 Planner，任務是「分析一家電商過去一年銷售數據，找出三個最有潛力的新品類，撰寫建議報告」。
   請只輸出一則訊息：{"schema_version":"2.0","type":"task_plan","sender":"planner","receiver":"executor_pool","msg_id":...,"timestamp":...,
   "payload":{"nodes":[{"id":...,"desc":...,"depends_on":[...],"input":...,"output":...}]}}，節點 6～12 個。
2. 程式檢查（不再呼叫模型）：
   a. 信封：六個必要欄位（type、sender、receiver、payload、timestamp、msg_id）都在；有 schema_version。
   b. 寬容接收者：寫一個 v1 接收器（只認得 v1 欄位），把模型訊息多加一個未知欄位 "priority" 後餵進去，應該忽略而不報錯；再刪掉 msg_id 餵進去，應該報錯。
   c. 可執行性：依賴都存在、無循環（Kahn 拓撲排序）。
   d. 可觀測性：每個節點都有非空 input 與 output。
   e. 最小性（啟發式）：desc 裡出現「並且」「然後」「以及」兩次以上的節點標記為「可能不是原子任務」。
   f. 並行度：算出關鍵路徑長度與最大並行寬度，並列出可以並行的節點組。
3. 把模型原始訊息與 a～f 的 PASS／FAIL 表寫進 ch02/interactive/planner_report.md，最後寫 3 行：這份 DAG 哪裡可以被 Monitor 盯、哪裡容易變成黑盒子。claude -p 只呼叫 1 次。
```

**觀察重點**：

- 模型的 DAG 是否無循環、而且真的有可並行的分支（不是一條直線）？
- 寬容接收者是否做到「未知欄位忽略、缺必要欄位報錯」兩件事？
- 有沒有節點被標成「可能不是原子任務」？這正是細微性權衡的例子。（每次模型輸出可能不同，照實記錄）
