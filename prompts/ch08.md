# ch08｜實務設計：角色定義、通訊、監督的落地框架

## 這章在講什麼

- 一個代理的錯誤會被其他代理當成可信輸入，錯誤像漣漪一樣擴散；落地框架的目標不是杜絕錯誤，而是「及時發現問題並安全地停下來」。
- 角色卡是每個代理的「職務說明書」：能做什麼、不能做什麼、出事找誰、跟誰互動。YAML 好讀好改、JSON Schema 能讓機器驗證，成熟做法是兩者並存。
- 熱更新角色卡會引發狀態不一致、通訊衝突、審計斷裂；安全流程分五階段：預備靜態檢查 → 沙箱驗證 → 灰度發布（偏差超閾值自動回滾）→ 全量切換 → 確認與審計。
- 通訊三件事：Message Bus 要冪等（訊息帶唯一 ID、接收端去重，預設冪等再選擇性放寬）；Event Sourcing 保存事件序列，可以重放還原「決策脈絡」；排序靠向量時鐘而非單純時間戳。
- 監督層：SLI／SLO 拆成基礎設施、單一代理、協作鏈路三層；人工介入的「紅色按鈕」要設計觸發條件（建議／強制兩級）、影響範圍、恢復流程與權限。
- 成本：GPU 時間拍賣可提高效率，但要保留容量、優先權與加權，避免關鍵任務餓死；開源／閉源模型混合調度，簡單任務用便宜模型、低信心才升級。

## 作者做過的實驗／例子

- 東南亞電商 47 分鐘雪崩：庫存代理讀到過時快取，把熱銷手機庫存寫成原本的 20 倍，透過 Message Bus 廣播給 7 個下游代理；定價代理降價到成本以下、物流派車、客服回覆三千多筆「庫存充足」。
- Event Sourcing 情境：把 14:31:22 的錯誤決策用時間區間縮小到 3000 筆事件，發現前 3 秒內兩條訊息只差 4ms，重放確認是競爭條件造成順序錯亂。
- 紅色按鈕情境：凌晨風控代理錯誤率升到 15%、已批准 120 筆高風險交易，先切到降級規則引擎再停該代理，避免支付斷鏈。
- 客服混合調度：意圖分類用輕量開源、標準查詢用規則引擎、複雜問題在開源信心低於 0.7 時才升級閉源，成本可降 60～80%。

## 教練解說要點

- 沒有熔斷時，一個錯誤數字會被 7 個代理同時「正確地」執行；監督層的價值就在擴散之前把它攔下。
- 冪等不是可有可無：網路重試必然發生，沒有去重就會重複扣款、重複派車。
- 灰度發布用「時間換安全」：多花十分鐘，換掉秒級雪崩的風險。
- 紅色按鈕是安全元件不是失敗標誌，停下來之後還要能「診斷→修復→灰度重啟→全量恢復」。

### 練習 1：庫存錯誤廣播：冪等、熔斷與灰度回滾的對照

**目的**：重現「一個錯誤數字經 Message Bus 擴散」的雪崩，量化去重、熔斷與灰度發布各擋下多少損失。
**送給練習視窗的提示詞**：

```text
寫 ch08/interactive/bus_sim.py（只用標準庫、random.seed(8)、不可 input()、30 秒內跑完）：
1. 實作一個極簡 Message Bus：訊息有 msg_id（格式 agent_id:timestamp:seq）、type、payload；接收端可選擇開啟「已處理 ID 去重」（只保留最近 N=500 個 ID 的時間窗）。網路有 15% 機率重送同一訊息。
2. 角色卡用 dict 表示（capabilities、constraints、dependencies），並寫一個 validate_card() 做 JSON Schema 風格檢查（必填欄位、型別、forbidden_actions 不可出現在 capabilities），對 3 張卡（1 張合法、2 張故意錯）印出檢查結果。
3. 模擬 60 個時間步：庫存代理在第 10 步把某商品庫存從 50 寫成 1000，廣播給定價、物流、客服等 7 個下游代理。下游行為：定價看到庫存>500 就降價、物流每則訊息派一台車、客服每步回覆 50 筆「庫存充足」。
4. 四種設定各跑一次並印成表：
   A 無防護；B 只開去重；C 去重 + 熔斷（監督層看到庫存單步變化 >5 倍就暫停該訊息類型，並在 3 步內通知人工）；D C 再加上灰度：新數值先只送 1 個下游，錯誤率超過閾值自動回滾。
   欄位：重複處理次數、錯誤派車數、低於成本成交筆數、錯誤客服回覆數、熔斷觸發時間步。
5. 結果存 ch08/interactive/bus_result.json。
```

**觀察重點**：

- 只開去重（B）是否消除了重複派車，但仍擋不住「錯誤本身」的擴散？
- 加上熔斷（C）後，損失是否集中在觸發前的少數幾步？
- 角色卡檢查是否抓到 forbidden_actions 與 capabilities 衝突的那張卡？

### 練習 2：真實模型當監督代理，決定要不要按紅色按鈕

**目的**：讓真實模型扮演監督層，根據 SLI 讀數決定介入等級，用程式規則檢查它的決策是否合乎紅色按鈕的四個維度。
**送給練習視窗的提示詞**：

```text
寫 ch08/interactive/red_button_agent.py：
1. 用 random.seed(88) 產生三層 SLI 快照（基礎設施：CPU、佇列深度；代理層：各代理錯誤率與 P99 延遲；協作層：訂單到出貨鏈路成功率），其中風控代理錯誤率 15%、已批准 120 筆高風險交易，支付代理正常但依賴風控。
2. 在腳本開頭把 practice/ 加入 sys.path（Path(__file__).resolve().parents[2]），from llm_agent import ask_json。
   呼叫 ask_json 一次，提示模型扮演監督代理，輸出 {"level":"none|advisory|forced", "scope":"agent|chain|swarm", "target":..., "fallback":..., "recovery_steps":[...], "needs_two_person_approval": true|false}。
3. 用程式規則判定：level 至少為 advisory；scope 不可是 swarm（只需停單一代理）；若停風控代理必須提供 fallback，否則判定為「支付斷鏈」；recovery_steps 必須涵蓋診斷、修復、灰度重啟、全量恢復；forced 等級必須要求雙人確認。
4. 印出逐條 PASS／FAIL 並存 ch08/interactive/red_button_agent.json（含原始回覆）。claude -p 只呼叫 1 次。
```

**觀察重點**：

- 模型有沒有直接「全部停掉」（scope=swarm）？那會讓支付流程整個斷掉。
- 有沒有想到先切降級規則引擎再停代理？
- 恢復流程是否不只是「重啟」，而是包含灰度重啟？
